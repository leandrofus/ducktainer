# ducktainer

[![CI](https://github.com/leandrofus/ducktainer/actions/workflows/ci.yml/badge.svg)](https://github.com/leandrofus/ducktainer/actions/workflows/ci.yml)

**Управление Docker одним бинарным файлом.** Веб-интерфейс в стиле CRM (правый клик на всём, сохранённые представления, канбан, палитра ⌘K), стеки compose с визуальным редактором, каталог приложений, логи и веб-терминалы в реальном времени, доступ в один клик к каждому порту контейнера, частные туннели и публикация через Cloudflare. Вход использует ваших **системных пользователей** (PAM), а сетевой доступ ограничен теми хостами, которые вы разрешили.

[English](README.md) · [Español](README.es.md) · [сайт ducktainer](https://leandrofus.github.io/ducktainer/)

- **Ничего не нужно устанавливать на удалённых хостах**: к ним подключаются по **SSH** (`docker system dial-stdio`, как `DOCKER_HOST=ssh://`), по TLS (`tcp://`, например удалённый `ducktainer expose`) или, для узлов за NAT или брандмауэром, через необязательный **агент с исходящим подключением** (тот же бинарный файл), который подключается обратно к серверу.
- **Минимальные привилегии**: служба работает от непривилегированного пользователя. `ducktainer setup` подстраивает её под то, как установлен Docker: группа сокета, rootless или только root. Только проверки паролей выполняются от root, во вспомогательном процессе, активируемом через сокет.
- **Контроль доступа**: список разрешённых IP/CIDR/имён хостов (соединения отбрасываются до TLS), роли из групп POSIX, автоматический TLS с закреплением сертификата и журнал аудита.
- **Языки**: английский, испанский и русский. Интерфейс следует языку браузера и может быть переключён из меню пользователя; CLI следует переменной `LANG`.

## Начало работы

### 1. Установка

**Пакеты (рекомендуется)**: RHEL/Alma/Rocky 9+, Fedora, Debian 12+, Ubuntu 22.04+ (amd64 и arm64). Пакет зависит от совместимого с Docker движка (`docker-ce`, `moby-engine`, `docker.io`, `podman-docker`…) и рекомендует плагин compose и SSH-клиент.

```sh
# RHEL / Fedora
curl -fLO https://github.com/leandrofus/ducktainer/releases/latest/download/ducktainer-latest.x86_64.rpm
sudo dnf install ./ducktainer-latest.x86_64.rpm

# Debian / Ubuntu
curl -fLO https://github.com/leandrofus/ducktainer/releases/latest/download/ducktainer_latest_amd64.deb
sudo apt install ./ducktainer_latest_amd64.deb
```

На arm64 используйте `ducktainer-latest.aarch64.rpm` или `ducktainer_latest_arm64.deb`. Эти ссылки всегда указывают на последний выпуск.

Пакет:

- создаёт пользователя `ducktainer` и группы `ducktainer-admins` / `ducktainer-viewers`;
- создаёт `/etc/ducktainer/secret.key` — ключ, который шифрует секреты в конфигурации;
- запускает `ducktainer setup`, чтобы определить, как установлен Docker (а на машинах с рабочим столом готовит меню «Пуск»);
- включает `ducktainer.service` и вспомогательный сокет `ducktainer-pam.socket`, слушающий на `http://127.0.0.1:9900`.

При обновлении настройки сохраняются, а служба перезапускается, только если она была запущена.

**Windows (MSI)**, в PowerShell от имени администратора:

```powershell
curl.exe -fLO https://github.com/leandrofus/ducktainer/releases/latest/download/ducktainer-latest-x64.msi
Start-Process msiexec -Wait -ArgumentList '/i ducktainer-latest-x64.msi'
```

Установщик:

- помещает `ducktainer.exe` в `C:\Program Files\ducktainer` и добавляет его в PATH;
- регистрирует службу `ducktainer` (`ducktainer serve` от имени LocalSystem, перезапускается при сбое), слушающую на `http://127.0.0.1:9900`, и пункт в меню «Пуск»;
- хранит данные в `C:\ProgramData\ducktainer`, доступном только SYSTEM и администраторам. В терминале администратора `ducktainer token`, `ducktainer allow` и `ducktainer auth` работают с конфигурацией службы.

Вход выполняется под учётными записями Windows (локальными или `ДОМЕН\пользователь`). Члены групп «Администраторы», `docker-users` и `ducktainer-admins` — администраторы; члены `ducktainer-viewers` получают доступ только для чтения. Роли определяются локальными группами, поэтому доменная группа учитывается, если она входит в одну из них. При обновлении конфигурация сохраняется, а при удалении `C:\ProgramData\ducktainer` остаётся на месте. Если Docker на машине ещё нет, установите его командой `ducktainer engine install` (ниже).

**Один бинарный файл** (любой Linux, macOS или Windows; без PAM в Linux и macOS вход только по токену, а в Windows также под учётными записями Windows):

```sh
./ducktainer serve            # http://127.0.0.1:9900, выводит токен доступа
./ducktainer ui               # то же самое, и открывает браузер
```

Без пакета данные хранятся в каталоге конфигурации пользователя (`~/.config/ducktainer` в Linux) или в каталоге, на который указывает `DUCKTAINER_HOME`; `ducktainer help` выводит точный путь.

**Windows без Docker Desktop.** `ducktainer engine` устанавливает за вас Docker Engine с открытым исходным кодом; выполните команды в терминале с правами администратора:

```powershell
.\ducktainer.exe engine install                 # контейнеры Linux: Docker в собственном дистрибутиве WSL 2
.\ducktainer.exe engine install --mode native   # контейнеры Windows: dockerd.exe как служба Windows
.\ducktainer.exe engine status
.\ducktainer.exe ui
```

- `wsl` (по умолчанию) создаёт дистрибутив WSL 2 `ducktainer` из образа Ubuntu (проверяется по SHA256SUMS Ubuntu), запускает там `docker.io` с systemd и добавляет хост `wsl` (`wsl://ducktainer`). При входе в систему задача запускает `ducktainer engine relay` для пользователя, выполнившего установку. Ретранслятор не даёт дистрибутиву остановиться, поэтому контейнеры не останавливаются, когда WSL стал бы его выключать. Он также предоставляет Docker дистрибутива через именованный канал, потому что дистрибутивы WSL принадлежат пользователю, а служба (LocalSystem) не может их запускать. Служба добавляет хост `wsl`, когда находит ретранслятор администратора, и эти контейнеры работают, пока этот пользователь находится в системе (`--no-keepalive` отключает задачу).
- `native` включает компонент Containers (и Hyper-V в Windows 10/11), устанавливает `dockerd.exe`, `docker.exe` и плагин compose в `C:\Program Files\Docker`, регистрирует службу `docker` и направляет хост `local` на `npipe:////./pipe/docker_engine`. `--version` и `--sha256` фиксируют версию Docker. В Windows Home компонента Containers нет: используйте `wsl`.
- Если Windows требует перезагрузки (для включения WSL или компонента), перезагрузите систему и выполните эту же команду снова.

### 2. Проверка того, как ducktainer подключается к Docker

```sh
sudo ducktainer setup --dry-run
```

```
socket:  /var/run/docker.sock  (root:docker 0660, standard path)
mode:    group
  · access through group docker (socket root:docker 0660)
```

| Обнаруженная установка | Служба работает от имени |
|---|---|
| Сокет доступен группе (`root:docker 0660`, любое имя группы) | `ducktainer` + эта группа |
| Rootless Docker (`/run/user/1000/docker.sock`) или rootless Podman (`/run/user/1000/podman/podman.sock`) | владелец сокета |
| Сокет только для root, Podman | root (с предупреждением) |
| Установлен, но ещё не запущен | то, что указано в юните `docker.socket`; Podman без активного сокета API: `podman.socket` включается сам (root) |

Результат записывается в `/etc/systemd/system/ducktainer.service.d/10-docker-access.conf`. Запускайте `sudo ducktainer setup` снова каждый раз, когда меняется установка Docker (`--socket PATH` задаёт сокет принудительно).

### 3. Выдача доступа

Учётные записи — это обычные системные пользователи, локальные или из LDAP/SSSD/FreeIPA. Их **роль** зависит от групп:

| Роль | Группы (по умолчанию) | Может |
|---|---|---|
| **Администратор** | `ducktainer-admins`, `docker` | всё: контейнеры, стеки, образы, терминалы, туннели, настройки, пользователи |
| **Только чтение** | `ducktainer-viewers` | просматривать контейнеры, стеки, образы, сети, тома и хосты; ничего не менять, не открывать терминалы, не просматривать и не скачивать файлы и не видеть другие настройки. Пароли в строках подключения скрыты |

```sh
sudo useradd -m ana && sudo passwd ana       # только если учётной записи ещё нет
sudo usermod -aG ducktainer-admins ana          # администратор  (или ducktainer-viewers: только чтение)
sudo ducktainer auth test ana                   # проверяет пароль и показывает итоговую роль
```

- Членство в группах проверяется каждые 5 минут, поэтому после удаления из группы доступ отзывается быстро.
- Группы можно изменить, а отдельных пользователей добавить командой `ducktainer auth set --admin-groups … --viewer-groups … --admin-users … --viewer-users …`. Сессии длятся 12 часов (`--session-hours`).
- `root` не может войти, пока вы не включите это (`ducktainer auth set --allow-root on`).
- 5 неудачных попыток за 10 минут блокируют дальнейшие попытки, пока самой старой из них не исполнится 10 минут.
- Интерфейс показывает всё это в разделе **Настройки → Доступ → Участники**: соответствие ролей группам, текущих участников каждой группы и руководство, которое формирует эти команды за вас.

### 4. Открытие доступа из сети

По умолчанию ducktainer слушает только локальную машину. Разрешите адреса, которым можно подключаться (IP-адреса, диапазоны CIDR или имена хостов; имена хостов переразрешаются каждую минуту, поэтому работает динамический DNS), и перезапустите службу:

```sh
sudo ducktainer allow add 192.168.1.0/24 office.example.com
sudo systemctl restart ducktainer       # теперь слушает на 0.0.0.0:9900, с TLS
```

- Все остальные отключаются до TLS. Локальная машина разрешена всегда.
- **Настройки → Доступ → Сеть** показывает адрес прослушивания, ваш собственный IP и правило, которое его пропускает. Список разрешённых можно редактировать там же; изменения применяются сразу. Есть также проверка «Будет ли разрешён этот адрес?».
- Сертификат TLS самоподписанный. Его отпечаток SHA-256 выводится при запуске, чтобы клиенты могли его закрепить. Чтобы использовать собственный сертификат, укажите `--cert/--key` в `DUCKTAINER_OPTS` (`/etc/ducktainer/ducktainer.env`); `--tls on|off` переопределяет автоматический выбор.
- Частные туннели (см. [Возможности](#возможности)) используют порты `41000-41099` сервера (`--tunnel-ports`): откройте их в брандмауэре, если хотите ими пользоваться.

### 5. Вход

Откройте `https://<server>:9900` и войдите под своим системным пользователем и паролем.

**Аварийный токен** выполняет вход как администратор и авторизует API (`Authorization: Bearer`). Хранится только его хеш, поэтому он показывается один раз: `sudo ducktainer token --rotate` создаёт и выводит новый. Чтобы разрешить вход только системным пользователям, отключите его командой `sudo ducktainer auth set --token-login off`. Те же переключатели есть в разделе **Настройки → Доступ → Вход**.

### 6. Добавление хостов Docker (необязательно)

```sh
# через агент с исходящим подключением (идеально для узлов за NAT или брандмауэром): сначала добавьте хост
# в Настройки → Хосты → Агент (исходящее подключение / Edge) или командой ниже; он получит собственный токен,
# затем на узле выполните команду из «Скопировать команду установки агента»:
ducktainer endpoint add worker-1 agent://          # выводит токен хоста
#   curl -fsSL -k --pinnedpubkey 'sha256//…' -H 'Authorization: Bearer <host token>' \
#     'https://<ducktainer-server>:9900/api/agent/install.sh?server=…' | sudo sh

# по SSH: на удалённом хосте ничего не устанавливается (доступ по ключу; пользователю должно быть разрешено использовать Docker)
sudo -u ducktainer ssh-keygen -t ed25519          # ключ в /var/lib/ducktainer/.ssh, добавьте его в authorized_keys удалённого хоста
ducktainer endpoint add prod ssh://deploy@prod.example.com      # --key FILE, чтобы использовать другой ключ

# или через прокси, на удалённом хосте:
ducktainer expose --allow <ducktainer-server-ip>   # выводит точную строку `ducktainer endpoint add …` для запуска здесь
```

Хостами можно также управлять в разделе **Настройки → Хосты**, а переключаться между ними можно в верхней части боковой панели.

- У каждого хоста-агента есть собственный токен, действительный только для этого хоста; токен администратора от агентов не принимается. Команда установки передаёт токен в заголовке, закрепляет сертификат этого сервера (без `--insecure`), устанавливает агент как службу systemd и оставляет токен на узле в `/etc/ducktainer-agent/agent.env` (только для root). Хосты, зарегистрированные более ранними версиями с токеном администратора, не принимаются, пока вы не выдадите им токен в разделе Настройки → Хосты и не переустановите агент.
- Если агенты не могут достучаться до порта из списка разрешённых, `serve --agent-listen :9901` открывает порт только для агентов (нужен токен, список IP-адресов не применяется).
- Агенты поддерживают версию сервера: когда она меняется, они скачивают новый бинарник, проверяют, что он запускается на узле, и перезапускаются в него, а при любой ошибке остаются на текущем (отключается для каждого хоста в «Настройки → Хосты»; сборки `dev` и Windows сами не обновляются). В пакетах лежат статические бинарники агента для amd64 и arm64, поэтому узлам не нужна конкретная glibc (RHEL 8 работает), а архитектура узла может отличаться от серверной. Агенты, установленные до этой версии, нужно переустановить один раз.
- Хосты `tcp://` должны использовать TLS, если они не на той же машине; без `--fingerprint` закрепляется сертификат, предъявленный при добавлении хоста.
- Для хостов SSH ключ хоста запоминается при первом подключении (`StrictHostKeyChecking=accept-new`); изменившийся ключ отклоняется.
- Учётные данные реестра можно ограничить некоторыми хостами (`--hosts` или в интерфейсе): compose на узле получает копию тех учётных данных, которые ему разрешено видеть.

#### Модель доверия

ducktainer управляет Docker API каждого хоста, что эквивалентно правам root на нём: тот, кто контролирует сервер ducktainer (или его учётные записи администраторов), контролирует все хосты. Защищайте эту машину и `/etc/ducktainer/secret.key` так же, как сами хосты. Чтобы редактировать стеки на узле, ducktainer запускает там вспомогательный контейнер (`ducktainer-files`), который монтирует `/` узла; он завершается после часа простоя.

## Возможности

- **Быстрый переход** (стартовая страница каждого хоста): каждый порт каждого контейнера, разделённый на веб-порты (открываются одним кликом) и порты TCP/UDP. Для известных сервисов (PostgreSQL, MySQL/MariaDB, MongoDB, Redis, RabbitMQ) строка подключения собирается с учётными данными из окружения compose. Метки compose переопределяют догадки: `ducktainer.url=https://app.example.com`, `ducktainer.url.<port>=…` и `ducktainer.kind.<port>=http|tcp`.
- **Частные туннели**: щёлкните порт правой кнопкой и выберите «Открыть туннель…», чтобы подключиться к нему через сервер ducktainer, в том числе к неопубликованным портам и портам на хостах за агентом или NAT. Туннель закрывается через 30 минут без подключений, в заданное время, либо остаётся открытым (в том числе после перезапусков), пока вы его не закроете. Он принимает подключения только с адреса, который его открыл, или с любого адреса, которому разрешён доступ к ducktainer.
- **Публикация в интернете через Cloudflare**: «Опубликовать в интернете…» на веб-порту публикует его с помощью `cloudflared` (скачивается и проверяется по контрольной сумме, если не установлен). Без учётной записи вы получаете случайный адрес `trycloudflare.com`; с API-токеном (Настройки → Cloudflare) каждый сервис получает постоянное имя на ваших собственных доменах. Доступ может быть публичным или ограниченным некоторыми IP-адресами/хостами, входом в ducktainer (при необходимости только для некоторых пользователей или групп) либо для тех, у кого есть секретная ссылка; срок его действия может истекать.
- **Меню «Пуск»**: на машине с рабочим столом веб-приложения её контейнеров можно добавить в меню «Containers» (Linux, записи freedesktop) или в Пуск › Программы › Containers (Windows), по одному или автоматически; меню обновляется само (в Linux — через пользовательский юнит systemd, который `ducktainer setup` устанавливает для всех пользователей). **Настройки → Доступ → Меню «Пуск»**.
- **Контейнеры**: таблица, сгруппированная по стекам, или канбан по состоянию (перетащите карточку в «Остановлен», чтобы остановить контейнер), сохранённые представления, массовые действия и быстрый просмотр. У каждой записи есть Обзор (CPU/память/сеть в реальном времени и активность), Логи, Терминал, Файлы, Производительность, Процессы, Конфигурация и Inspect.
- **Редактирование контейнеров**: Docker не может изменить контейнер на месте, поэтому ducktainer создаёт новый контейнер с изменёнными настройками, меняет имена местами и удаляет старый. Тома сохраняются, а исходный контейнер восстанавливается, если новый не запустился. Контейнеры также можно переименовать, дублировать, обновить (загрузка + пересоздание) и зафиксировать в образ.
- **Стеки compose**:
  - **визуальный редактор** (YAML остаётся источником истины: комментарии, форматирование и переменные сохраняются) и редактор YAML;
  - проекты из нескольких файлов (базовый + переопределения) с объединённым представлением и «объединить в один файл»;
  - проверка перед сохранением (`docker compose config`), развёртывание и обновление, объединённые логи по сервисам;
  - стеки, созданные вне ducktainer, обнаруживаются и редактируются на месте либо принимаются в ducktainer;
  - стек может храниться в хранилище ducktainer или в каталоге по вашему выбору, в том числе на удалённых узлах.
- **Режим Swarm**: если хост входит в swarm, в боковой панели появляется группа Swarm:
  - **Кластер**: создать swarm или присоединиться к нему, команды присоединения для worker и менеджеров (с обновлением токенов), выход из swarm;
  - **Сервисы**: создание (образ, реплики или global, порты, окружение, overlay-сети, secrets, configs, ограничения, лимиты), масштабирование, перезапуск, обновление образа, откат, редактирование полной спецификации, задачи по узлам и логи в реальном времени;
  - **Стеки swarm**, развёрнутые через `docker stack deploy` из compose-файла и `.env` (те же редакторы, что и для стеков compose). Как и стеки compose, они хранятся в хранилище ducktainer или в собственном каталоге, в том числе на удалённых узлах; сервисы с `build:` (и `image:`, задающим имя результата) собираются там перед развёртыванием и при желании отправляются в реестр, чтобы их могли скачать все узлы. Стеки, развёрнутые вне ducktainer, видны в списке и могут быть приняты вставкой их compose или указанием их каталога. Шаблоны Swarm из маркетплейса разворачиваются здесь;
  - **Узлы**: доступность (active, pause, drain), повышение/понижение, метки, задачи по узлу, удаление;
  - **Secrets и configs**: создание из текста или файла, какие сервисы их используют.
  На worker видна только страница кластера: swarm управляется с хоста-менеджера.
- **Образы**: загрузка и отправка с прогрессом по слоям, тегирование, сборка из Dockerfile, история слоёв, очистка.
- **Сети**: реестр с подключёнными контейнерами и их IP-адресами, карта соединений, создание, подключение и отключение.
- **Тома**: кто использует каждый том, неиспользуемые тома, размеры и просмотр их содержимого через запущенный контейнер, который их монтирует.
- **Каталог приложений**: 26 встроенных приложений плюс любой список шаблонов Portainer v2/v3. Официальный список Portainer включён по умолчанию; список сообщества (~800 приложений, Lissy93) предварительно настроен, но выключен. Источники управляются в разделе Настройки → Каталог приложений.
- **Панель и активность**: сводка по хосту, использование диска и очистка, а также поток событий Docker в реальном времени.
- **Журнал аудита**: каждый вход и каждое действие записи или терминала, в разделе Настройки → Аудит и в `journalctl -u ducktainer`.

## Командная строка

| Команда | Назначение |
|---|---|
| `ducktainer serve` | Веб-интерфейс + API (`--listen`, `--allow`, `--tls auto\|on\|off`, `--cert/--key`, `--expose :2376 [--expose-read-only] [--expose-no-exec]`, `--agent-listen :9901`, `--tunnel-ports 41000-41099`) |
| `ducktainer ui` | Как `serve` на 127.0.0.1, и открывает браузер |
| `ducktainer agent` | Агент с исходящим подключением (`--server`, `--name`, `--fingerprint`, `--socket`, `--install-service`; токен в `DUCKTAINER_AGENT_TOKEN`) |
| `ducktainer expose` | Публикует только Docker API, с защитой (список разрешённых + токен + TLS; `--read-only`, `--no-exec`) |
| `ducktainer engine install [--mode wsl\|native] \| status \| relay` | Windows: установка Docker без Docker Desktop |
| `ducktainer setup [--dry-run] [--socket PATH]` | Приведение службы в соответствие с установкой Docker |
| `ducktainer install-service [serve flags]` | Установка службы systemd для одиночного бинарного файла (root) |
| `ducktainer auth show \| set … \| test <user>` | Вход системными пользователями и сопоставление ролей |
| `ducktainer allow ls \| add \| rm` | Список разрешённых сетей |
| `ducktainer token [--rotate]` | Создание и вывод нового аварийного/API-токена (хранится только его хеш, поэтому без `--rotate` он показывается только сразу после создания) |
| `ducktainer endpoint ls \| add \| rm` | Хосты Docker (`unix://`, `ssh://user@host`, `tcp://host:2376`, `agent://`, `wsl://distro`) |
| `ducktainer registry ls \| add \| rm` | Учётные данные приватного реестра (пароль через stdin; `--hosts` ограничивает, какие хосты их получают) |
| `ducktainer ps \| logs \| sh` | Контейнеры по стекам · логи контейнера или всего стека · интерактивная оболочка (выбирает bash/ash/sh); `-e <host>` выбирает хост |
| `ducktainer docker-env <host>` | `eval "$(ducktainer docker-env prod)"`, чтобы использовать docker CLI с хостом |
| `ducktainer version` | Вывод версии |

## Файлы

| Путь | Содержимое |
|---|---|
| `/etc/ducktainer/ducktainer.env` | `DUCKTAINER_OPTS` для `ducktainer serve` |
| `/etc/ducktainer/secret.key` | ключ, который шифрует секреты в конфигурации (только для root, передаётся службе через systemd `LoadCredential`) |
| `/etc/pam.d/ducktainer` | стек PAM для входа (`password-auth` в RHEL, `common-auth` в Debian) |
| `/var/lib/ducktainer/` | `config.json`, стеки (`stacks/<host>/<name>`), журнал аудита, сертификат TLS, SSH-ключи службы, загруженный `cloudflared` |
| `/etc/systemd/system/ducktainer.service.d/10-docker-access.conf` | создаётся `ducktainer setup` |
| `/usr/local/share/applications/ducktainer-containers/` | записи меню «Пуск» (машины с рабочим столом) |

Секреты в `config.json` (секрет сессии, токены хостов, пароли реестров, токены Cloudflare, секретные ссылки) шифруются AES-256-GCM, а аварийный токен хранится только как хеш SHA-256. Ключ хранится отдельно от данных, поэтому копия или резервная копия `/var/lib/ducktainer` без ключа ничего не раскрывает. Сохраняйте `/etc/ducktainer/secret.key` отдельно: без него конфигурацию нельзя прочитать. Для бинарного файла, запущенного без пакета, ключ — это `secret.key` в каталоге данных, если только `DUCKTAINER_KEY_FILE` не указывает на другое место. Конфигурации в открытом виде из более ранних версий шифруются при первом запуске.

## Переводы

Английский — исходный язык. Чтобы добавить язык:

1. Скопируйте `web/src/i18n/es.ts` (интерфейс) и `internal/i18n/es.go` (ошибки API и CLI). Ключи — это английские строки; ключи `ctx|text` — варианты рода/числа, которые используются в `tc()`.
2. Зарегистрируйте новый каталог в `web/src/i18n/index.ts` и `internal/i18n/i18n.go`.

## Разработка

```sh
make help           # показать все доступные цели make
make run            # собрать и запустить ducktainer serve локально (http://127.0.0.1:9900; ARGS="..." для флагов)
make ui             # собрать и запустить ducktainer ui (открывает браузер)
make build          # веб-интерфейс + статический бинарный файл (без PAM) в bin/
make build-pam      # с PAM (нужны gcc и pam-devel / libpam0g-dev)
make test           # модульные тесты Go + проверка типов веба (test-unit, test-race, test-web по отдельности)
make dev            # интерфейс с горячей перезагрузкой против запущенного `ducktainer serve` на :9900
make packages       # rpm + deb (amd64, arm64), собираются в контейнере; нужен только Docker
make dist           # статические бинарные файлы для linux/darwin/windows
make clean          # удалить артефакты сборки
```

Структура:

- `main.go`: CLI.
- `internal/server`: API HTTP/WebSocket, экран быстрого перехода, туннели, публикации Cloudflare, синхронизация меню «Пуск».
- `internal/docker`: клиент Engine API (unix, ssh, tcp+tls, npipe, agent).
- `internal/agent`: агент с исходящим подключением и его туннель.
- `internal/auth`: PAM, роли и вспомогательный процесс root.
- `internal/setup`: определение установки Docker.
- `internal/engine`: установка Docker в Windows (WSL 2 / native).
- `internal/cloudflare`: `cloudflared` и API Cloudflare.
- `internal/shortcuts`: записи меню «Пуск» (Linux, Windows).
- `internal/compose`, `internal/templates`, `internal/proxy`, `internal/access`, `internal/config`, `internal/probe`, `internal/tlsutil`, `internal/cli`, `internal/i18n`.
- `packaging/`: юниты systemd, файлы PAM, nfpm.
- `web/`: React + Vite.
- `site/`: сайт (Astro).
